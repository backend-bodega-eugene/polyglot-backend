# thsService 接口设计与开发顺序

## 1. 文档目的

本文档用于确定后端功能边界、接口设计和开发顺序，是后续实现接口的主要依据。

`接口清单.md` 来自现有前端页面，可以用于了解页面需要展示哪些数据，但其中的接口命名、字段、校验规则和业务逻辑不直接视为最终后端设计。实现接口前，应以本文档、实际前端调用和已确认的业务规则为准。

当前项目是模拟证券业务，不连接真实券商交易系统。行情、新闻和理财数据的数据来源尚未确定，开发初期可以使用数据库种子数据，但接口结构应保持可替换数据源。

## 2. 总体原则

### 2.1 登录要求

除以下接口外，所有业务接口默认都需要登录：

- 用户注册
- 用户登录
- 服务存活检查
- 服务就绪检查
- 开发环境 Swagger 文档

需要登录的接口统一携带：

```http
Authorization: Bearer <accessToken>
```

第一阶段先完成注册和登录。JWT 鉴权中间件随后接入其他业务接口。

### 2.2 API 前缀

当前 App 端业务接口统一使用：

```text
/api/app
```

未来后台管理接口使用 `/api/admin` 前缀，并采用独立的路由分组、身份体系和权限控制。当前阶段只开发 App 端接口，不实现后台管理功能。

健康检查不使用业务版本前缀：

```text
GET /health/live
GET /health/ready
```

### 2.3 统一响应

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "requestId": "01J..."
}
```

失败响应：

```json
{
  "code": 40001,
  "message": "用户名或密码错误",
  "data": null,
  "requestId": "01J..."
}
```

分页响应的 `data` 统一为：

```json
{
  "list": [],
  "page": 1,
  "pageSize": 20,
  "total": 0
}
```

### 2.4 数据职责

- 用户 ID 只能从登录凭证中取得，不能由客户端指定。
- 密码只接收原始输入并立即进行安全哈希，任何响应和日志都不得返回密码或密码哈希。
- 金额、价格、收益和手续费由服务端计算，数据库使用 `DECIMAL` 保存。
- 买卖接口不能信任客户端提交的股票名称、成交价、手续费、余额或持仓。
- 股票名称来自证券基础数据，模拟成交价来自服务端行情快照。
- 总资产、总市值、盈亏和仓位比例由服务端根据账户、持仓和行情计算。
- 客户端展示字段可以逐步增加，但核心业务字段必须有明确来源。

## 3. 开发阶段总览

| 阶段 | 模块 | 目标 | 前置依赖 |
|---|---|---|---|
| 1 | 注册与登录 | 建立用户体系并签发 JWT | MySQL、配置、统一响应 |
| 2 | 鉴权与用户信息 | 保护业务接口并验证当前用户 | 阶段 1 |
| 3 | 证券基础数据与搜索 | 建立股票主数据，为自选和交易提供统一标的 | 阶段 2 |
| 4 | 自选股 | 保存每个用户的关注列表 | 阶段 3 |
| 5 | 行情 | 提供服务端价格和市场展示数据 | 阶段 3、数据源或种子数据 |
| 6 | 模拟账户与持仓 | 建立资金账户、持仓和资产查询 | 阶段 2、阶段 3、阶段 5 |
| 7 | 模拟买卖 | 完成事务、费用、T+1 和成交记录 | 阶段 6 |
| 8 | 首页聚合 | 组合热点、推荐和热榜 | 行情及内容数据 |
| 9 | 资讯 | 提供资讯列表和详情 | 内容数据源或种子数据 |
| 10 | 理财 | 提供理财产品和主题展示 | 产品数据源或种子数据 |

开发时应完成一个阶段的数据库迁移、业务代码、测试和 Swagger，再进入依赖它的下一阶段。

## 4. 第一阶段：注册与登录

这是第一个需要实现的业务阶段。

### 4.1 用户注册

```text
POST /api/app/auth/register
```

不需要登录。

请求：

```json
{
  "account": "13800138000",
  "realName": "张三",
  "password": "Example123"
}
```

规则：

- `account` 必填，必须是 11 位中国大陆手机号或合法邮箱。
- 后端识别账户类型，并分别写入 `phone` 或 `email` 字段。
- 邮箱去除首尾空格并转换为小写；手机号和邮箱分别保持唯一。
- `realName` 必填，去除首尾空格后长度必须为 2～64 个字符。
- `password` 必填，长度必须为 8～72 个字节。
- `confirm` 只属于前端交互，不发送给后端。
- 密码使用 bcrypt 哈希，禁止保存明文。
- 同一个 IP 一分钟内只能访问注册接口一次，失败请求也计入限流。
- 手机号或邮箱冲突时返回明确且稳定的业务错误码。
- 注册成功后可以直接返回 Token，减少用户再次登录；第一版采用此方式。
- 当前注册流程只创建用户，不创建模拟资金账户。

响应数据：

```json
{
  "accessToken": "...",
  "tokenType": "Bearer",
  "expiresIn": 7200,
  "user": {
    "id": 1,
    "account": "138****8000",
    "realName": "张三"
  }
}
```

### 4.2 用户登录

```text
POST /api/app/auth/login
```

不需要登录。

请求：

```json
{
  "account": "13800138000",
  "password": "example-password"
}
```

规则：

- `account` 可以是手机号或邮箱。
- 用户不存在和密码错误统一返回“账户或密码错误”，避免泄露账号是否存在。
- 同一个 IP 一分钟内最多访问登录接口 5 次，超过后返回 HTTP 429。
- 登录成功签发带过期时间的 JWT Access Token。
- JWT 至少包含用户 ID、签发时间、过期时间和唯一 Token ID。
- JWT 密钥从环境变量读取，不能写入源码。
- 第一版暂不实现 Refresh Token；确有长期登录需求时再单独增加。
- 第一版退出登录由客户端删除 Token 完成；需要服务端主动失效能力时再增加 Token 撤销机制。

响应与注册成功响应一致。

### 4.3 第一阶段所需数据表

#### `users`

建议字段：

- `id`
- `phone`
- `email`
- `real_name`
- `password_hash`
- `status`
- `last_login_at`
- `created_at`
- `updated_at`

手机号和邮箱允许其中一个为空，但至少必须填写一个，并分别建立唯一索引。模拟资金账户的结构和结算规则确认后，再单独设计账户相关表。

## 5. 第二阶段：鉴权与当前用户

### 5.1 获取当前用户

```text
GET /api/app/users/me
```

需要登录。

用途：

- 验证 Token 是否有效。
- 前端应用启动时恢复用户状态。
- 返回当前用户的基础资料，不返回资金和持仓。

响应数据：

```json
{
  "id": 1,
  "account": "138****8000",
  "realName": "张三",
  "createdAt": "2026-10-06T10:00:00+08:00"
}
```

### 5.2 鉴权中间件

鉴权中间件负责：

- 读取并校验 Bearer Token。
- 校验签名和过期时间。
- 将用户 ID 写入请求上下文。
- 对缺少、无效或过期 Token 统一返回 `401 Unauthorized`。

从本阶段开始，后续所有业务接口都挂载鉴权中间件。

## 6. 第三阶段：证券基础数据与搜索

自选、行情、持仓和交易都依赖统一的证券代码，因此先建立证券基础数据。

### 6.1 搜索证券

```text
GET /api/app/stocks?keyword=&market=&page=1&pageSize=20
```

需要登录。

规则：

- 支持按代码和名称搜索。
- `keyword` 为空时返回默认或热门列表。
- `market` 可选，例如 `CN`、`HK`、`US`。
- 返回稳定的证券 ID、代码、名称、市场和交易状态。
- 不能只用 `code` 作为全局唯一标识，因为不同市场可能出现相同代码；应使用证券 ID，或使用 `market + code` 唯一键。

响应列表项：

```json
{
  "id": 1,
  "market": "CN",
  "code": "000001",
  "name": "平安银行",
  "price": "11.25",
  "changePct": "1.32",
  "tradable": true
}
```

价格字段来自行情数据，不保存在证券主表中作为权威价格。

## 7. 第四阶段：自选股

原清单建议的 `POST /api/watchlist/toggle` 不具备幂等性。网络重试可能导致状态被反转，因此改为明确的增加和删除接口。

### 7.1 查询自选股

```text
GET /api/app/watchlist?page=1&pageSize=50
```

需要登录。只返回当前用户的自选股。

### 7.2 添加自选股

```text
PUT /api/app/watchlist/{stockId}
```

需要登录。重复添加视为成功，不重复创建记录。

### 7.3 删除自选股

```text
DELETE /api/app/watchlist/{stockId}
```

需要登录。目标不存在时也可以视为成功。

自选列表中的实时价格、涨跌幅等展示数据由行情模块补充，不重复存入自选表。

## 8. 第五阶段：行情

第一版采用公开行情快照与模拟降级数据组合：

- 腾讯行情：A股、港股、美股、ETF、可转债、全球指数和国际商品。
- 新浪行情：国内期货、沪金和沪银。
- 第三方未返回数据时，优先使用最近一次成功缓存；没有缓存时使用数据库种子模拟值。
- 对外通过 `dataStatus` 标记 `live`、`stale` 或 `mock`。
- 行情缓存时间通过配置管理，开发环境默认 5 分钟，生产环境默认 10 分钟。

### 8.1 统一分类行情接口

```text
GET /api/app/market/quotes?category={category}
```

需要登录，分类枚举如下：

| category | 页面分类 |
|---|---|
| `global` | 全球 |
| `a_stock` | A股 |
| `hk_stock` | 港股 |
| `us_stock` | 美股 |
| `etf` | ETF |
| `future` | 期货 |
| `gold` | 黄金 |
| `convertible_bond` | 可转债 |
| `other` | 其他 |

所有分类使用相同列表结构，包含证券代码、名称、市场、币种、最新价、涨跌额、涨跌幅、行情时间和数据状态。第一版为每个分类配置 10 个标的。标的名单、排序和模拟降级值由 `market_instruments` 表管理，最新行情保存在 `market_quote_cache` 表。

第一版先完成与参考页面一致的分类列表。板块轮动、资金流、热度、排行和市场宽度等扩展模块允许使用独立模拟数据，拿到对应数据源后再替换，不改变基础行情列表接口。

## 9. 第六阶段：模拟账户与持仓

### 9.1 查询资产和持仓

```text
GET /api/app/portfolio/positions
```

需要登录。

返回：

- 总资产
- 现金
- 可用资金
- 冻结资金
- 持仓市值
- 浮动盈亏
- 当日盈亏
- 仓位比例
- 持仓摘要列表

当前演示版已实现，返回 `simulated: true`、`account` 和 `positions`。首次仅携带Token访问时，默认按人民币200000元生成3至5只A股持仓，每只固定15条模拟买卖成交并落库；后续不传参数直接查询已保存快照。

传入 `totalAssets` 查询参数会重建当前快照，例如 `GET /api/app/portfolio/positions?totalAssets=350000.50`。总资产范围为 10000 至 1000000000 元，最多两位小数。新快照替换当前展示内容，旧持仓和成交仍保留在数据库中。

金额以十进制字符串返回，币种 `CNY`，总资产＝总市值＋可用现金，可取现金＝可用现金。浮动盈亏为所有持仓的现价市值减买入成本，当日盈亏根据行情涨跌额和持仓数量计算。买入数量按 100 股整手生成，成本低于生成时的行情价；买入日期早于生成日期，因此可用数量等于持仓数量。生成后保存固定行情快照，查询不会自动变更价格与资产。持仓与成交均为演示数据，不含手续费。

```text
GET /api/app/portfolio/trades?page=1&pageSize=20
```

历史成交接口同样需要登录，查询当前快照对应的买入和卖出成交，按成交时间倒序。`page`默认1，`pageSize`默认20，最大100；尚未生成持仓时返回空数组。资产、持仓及历史成交均从Token获取当前用户，不接受客户端指定用户ID。

数据库迁移 `000004_create_demo_portfolio` 创建 `demo_portfolio_accounts`、`demo_portfolio_positions`、`demo_portfolio_trades` 三张表。初始化和重建使用数据库事务，并锁定用户行处理同一用户的并发请求。

### 9.2 查询单个持仓明细

已实现分类模拟持仓接口：

```text
GET /api/app/market/holdings?category=a_stock
GET /api/app/market/holdings?category=a_stock&totalAssets=700000
```

需要登录，category支持九个分类。原行情接口 `/api/app/market/quotes` 保持不变。此接口不返回行情列表或quote字段；items仅包含当前分类的3至5个非零持仓，每个包含position、positionRatio和恰好15条trades，按成交时间倒序。

按user_id与category独立保存。传totalAssets时物理删除当前分类旧快照并重新随机选股、生成持仓和交易；不传且已有记录时直接读库，不访问外部行情、不重新生成；不传且没有记录时随机生成200000至1000000元整数总资产并落库。totalAssets允许10000至1000000000元、最多两位小数。

各分类独立使用自己的总资产，互不合计；不修改原portfolio接口的资产、持仓和成交。总资产等于该分类持仓市值加现金。资产、市值和盈亏为人民币，成本价、现价及成交金额为原币种，USD/CNY按7.10、HKD/CNY按0.91的固定演示汇率折算。税费及已实现盈亏暂为0，交易净数量等于持仓数量。无未持有标的和零持仓项。现价仍作为持仓必要字段保留，内部生成时复用行情源。

迁移000007_category_demo_holdings创建demo_category_holdings表，保存总资产DECIMAL及完整JSON快照，用户和分类为联合主键。删除及重建在同一事务中执行，失败回滚保留原数据。按用户加锁避免重复初始化；每个分类最多一条当前快照。响应id仅在对应category与generation内唯一。旧版共享账户数据不再作为此接口的数据来源，原portfolio接口保持其现有行为。

以下单个持仓明细路径为后续规划：

```text
GET /api/app/portfolio/positions/{stockId}
```

需要登录。

返回当前用户对指定证券的持仓、可卖数量、成本、最新价格、盈亏和相关成交记录。原清单中的 `GET /api/deal/hold-detail?code=` 调整为资源路径，且通过登录用户限定数据范围。

### 9.3 查询资金流水

```text
GET /api/app/portfolio/cash-flows?page=1&pageSize=20
```

需要登录。用于解释余额变化和排查交易问题。

## 10. 第七阶段：模拟买卖

### 10.1 模拟买入

```text
POST /api/app/trades/buy
```

需要登录。

请求：

```json
{
  "stockId": 1,
  "amount": 100,
  "idempotencyKey": "client-generated-unique-key"
}
```

服务端负责：

- 检查证券存在且可交易。
- 从服务端行情获取模拟成交价。
- 校验数量为 100 的整数倍。
- 计算佣金和所需资金。
- 锁定账户，检查可用资金。
- 写入订单、成交、持仓批次和资金流水。
- 更新账户余额和汇总持仓。
- 在同一数据库事务中完成全部操作。
- 使用幂等键防止重复提交。

### 10.2 模拟卖出

```text
POST /api/app/trades/sell
```

需要登录。

请求字段与买入相同。服务端额外负责：

- 检查可卖数量。
- 执行 T+1，当日买入批次不能卖出。
- 计算佣金和印花税。
- 更新持仓批次、汇总持仓、账户和资金流水。
- 在同一数据库事务中完成全部操作。

### 10.3 查询成交记录

```text
GET /api/app/trades?page=1&pageSize=20&stockId=
GET /api/app/trades/{tradeId}
```

需要登录，只能查询当前用户的成交记录。

原清单让客户端提交 `name` 和 `price`，这种设计会允许客户端伪造成交标的和成交价，因此不采用。

## 11. 第八阶段：首页聚合

首页数据是展示层聚合，不应早于其依赖的数据开发。

保留以下接口：

```text
GET /api/app/home/hot-picks
GET /api/app/home/feed
GET /api/app/home/hot-rank
```

全部需要登录。

开发前应先确认：

- 数据是人工维护、数据库种子数据还是第三方来源。
- 首页推荐是否对所有用户相同。
- 是否需要按用户自选和浏览行为个性化。
- 数据更新时间、缓存时间和失效策略。

第一版建议返回所有用户共享的内容，不实现推荐算法。

## 12. 第九阶段：资讯

原清单只定义了资讯集合，没有正式定义详情接口。应拆分为列表和详情。

```text
GET /api/app/news?page=1&pageSize=20&type=
GET /api/app/news/{newsId}
```

全部需要登录。

列表返回摘要，详情返回正文，避免列表接口携带大量正文内容。视频、快讯和专题如果数据结构差异明显，应使用独立接口或明确的内容类型，不能依赖一个包含大量可选字段的万能对象。

## 13. 第十阶段：理财

理财功能与模拟股票交易没有直接依赖，优先级最低。数据源和业务目标明确后再实现。

建议拆分为：

```text
GET /api/app/wealth/products?page=1&pageSize=20
GET /api/app/wealth/products/{productId}
GET /api/app/wealth/themes
```

全部需要登录。

如果第一版只用于页面展示，可以先提供只读种子数据，不实现申购、赎回和真实收益计算。

## 14. 原接口清单需要调整的内容

| 原设计 | 调整方式 | 原因 |
|---|---|---|
| 接口可能返回对象，也可能包在 `{data: ...}` 中 | 统一响应格式 | 降低前后端判断和错误处理成本 |
| `POST /watchlist/toggle` | 改为 `PUT` 和 `DELETE` | 保证请求幂等，支持安全重试 |
| 买卖由客户端提交 `name`、`price` | 只提交 `stockId` 和数量 | 防止伪造标的和成交价 |
| 持股明细使用 `?code=` | 使用 `/portfolio/positions/{stockId}` | 明确资源关系并隔离当前用户数据 |
| 只有资讯集合，没有详情接口 | 增加 `/news/{newsId}` | 支持正式的资讯详情页 |
| 大量接口没有分页 | 列表接口统一预留分页 | 防止数据增长后一次返回过多内容 |
| 股票只使用 `code` | 使用 `stockId`，数据库约束 `market + code` | 避免跨市场代码冲突 |
| 页面传入或本地计算资产数据 | 服务端统一计算 | 保证资金和持仓数据一致 |
| 行情字段一次性全部固化 | 先确认数据源，再实现实际字段 | 避免形成无法提供数据的空接口 |
| 注册请求包含 `confirm` | 仅在前端校验确认密码 | 后端无需接收重复密码 |
